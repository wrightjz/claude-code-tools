# Spec Command

A lightweight command to quickly capture project specifications. Unlike `/create-prd` (heavy interview process), `/spec` is fast and focused - designed to get to a workable spec in minutes, not hours.

## Command Syntax

```
/spec "DESCRIPTION"
```

**Parameters:**
- `DESCRIPTION` (required): One sentence describing what you're building

## Output

Single file: `docs/spec.md`

---

## Process

### Step 1: Quick Context Gather

Ask exactly ONE round of questions using AskUserQuestion. Include 3-4 questions max:

```
Given: "[DESCRIPTION]"

1. **Scope**: What's the ONE thing this must do to be useful?
   - A) [Infer simplest version]
   - B) [Infer slightly larger scope]
   - C) [Infer full vision]

2. **Context**: Is this a new project or adding to existing code?
   - A) New project (greenfield)
   - B) Adding to existing codebase
   - C) Refactoring existing code

3. **Stack** (if not obvious from context): What's the tech stack?
   - A) [Infer from description]
   - B) [Common alternative]
   - C) Other (specify)

4. **Timeline pressure**: How polished does v1 need to be?
   - A) Quick prototype (works, might be rough)
   - B) Production-ready (solid, tested)
   - C) Enterprise-grade (bulletproof, documented)
```

Adapt these questions based on the description. Skip questions where the answer is obvious from context.

### Step 2: Generate Spec

After receiving answers, generate `docs/spec.md`:

```markdown
# [Project Name] Spec

> [One-sentence description]

## Goal

[2-3 sentences on what success looks like]

## Scope

### Must Have (v1)
- [ ] [Core functionality 1]
- [ ] [Core functionality 2]
- [ ] [Core functionality 3]

### Out of Scope (for now)
- [Thing that might be expected but we're not building]
- [Another exclusion]

## Context

- **Type**: [New project | Addition | Refactor]
- **Stack**: [Tech stack]
- **Quality bar**: [Prototype | Production | Enterprise]

## Technical Notes

[Any relevant technical context - existing code to integrate with, APIs to use, constraints to respect]

## Open Questions

- [ ] [Any unresolved question that emerged]

---

*Generated by /spec - Ready for `/plan` to break into stories*
```

---

## Design Principles

1. **Speed over thoroughness**: Get a working spec in 2-3 minutes
2. **Good enough > perfect**: The spec will be refined during planning
3. **One round of questions**: No back-and-forth interview
4. **Opinionated defaults**: Make reasonable assumptions, note them
5. **Clear handoff**: Output explicitly designed for `/plan` consumption

## Examples

### Example 1: Simple Feature

**User:** `/spec "Add dark mode toggle to the settings page"`

**Agent asks:**
```
Quick context for the dark mode toggle:

1. **Scope**: What's the core requirement?
   A) Just the toggle UI (theme switching handled elsewhere)
   B) Toggle + theme persistence (localStorage)
   C) Full theme system with CSS variables

2. **Timeline**: How polished?
   A) Quick prototype
   B) Production-ready
```

**User:** `1B, 2B`

**Generated spec:**
```markdown
# Dark Mode Toggle Spec

> Add a dark mode toggle to settings that persists user preference

## Goal

Users can switch between light and dark themes from the settings page.
Their preference persists across sessions via localStorage.

## Scope

### Must Have (v1)
- [ ] Toggle switch component in settings
- [ ] Theme state management (light/dark)
- [ ] localStorage persistence
- [ ] Apply theme to existing components

### Out of Scope (for now)
- System preference detection (prefers-color-scheme)
- Per-page theme overrides
- Theme customization beyond light/dark

## Context

- **Type**: Addition to existing codebase
- **Stack**: [Inferred from project - e.g., React + Tailwind]
- **Quality bar**: Production-ready

## Technical Notes

- Use existing Button/Toggle components
- Theme CSS variables likely already exist (verify)
- Consider existing ThemeContext if present

## Open Questions

- [ ] Do CSS variables for theming already exist?

---

*Generated by /spec - Ready for `/plan` to break into stories*
```

## When to Use /spec vs /create-prd

| Use `/spec` when... | Use `/create-prd` when... |
|---------------------|---------------------------|
| You know roughly what you want | Requirements are fuzzy |
| Solo project or small team | Multiple stakeholders |
| Feature addition | Complex new product |
| You want to start coding soon | You need alignment docs |
| Spec will evolve during build | Spec needs sign-off first |

---

## Failure Modes to Avoid

1. **Over-questioning**: This is NOT an interview. One round, done.
2. **Scope creep in spec**: Keep Must Have to 3-5 items max
3. **Premature architecture**: Save technical decisions for planning
4. **Vague scope**: "Make it good" is not a scope item
